## 4. Part 8: areas compared

| District | Stored (km2) | Geodesic (km2) | Web Mercator (km2) | Mercator / geodesic | Latitude | 1/cos^2(lat) |
|---|---|---|---|---|---|---|
| Gwadar | 11,574 | 11,575 | 14,245 | 1.23 | 25.4 N | 1.23 |
| Lahore | 1,730 | 1,730 | 2,385 | 1.38 | 31.5 N | 1.37 |
| Gilgit | 4,016 | 4,015 | 6,133 | 1.53 | 35.9 N | 1.52 |

The geodesic area is the true area on the ellipsoid and is close to the
stored figure. The Web Mercator area is always larger, and the ratio grows
with latitude: Mercator stretches distances by 1/cos(latitude) in both
directions, so areas are inflated by about 1/cos^2(latitude), as the last
two columns show. Gwadar, the southernmost, is inflated least and Gilgit,
the northernmost, most. Areas must therefore never be measured in EPSG:3857.

## 5. Answers to the questions

**1. In Labs 2 and 3, every visitor downloaded the whole GeoJSON file. What can a page backed by Django and PostGIS do instead?**

The server can send only what is asked for, and can answer questions
without sending geometry at all. Two examples from this lab:

- `/api/districts/?province=Sindh` filters in the database and returns
  only the 29 Sindh districts instead of all 160.
- `/api/where/?lat=...&lng=...` runs a point-in-polygon query in PostGIS
  and returns a few bytes of JSON naming the district, instead of the
  browser downloading about 1 MB of boundaries to work it out itself.

The data is also live: an edit saved in the admin appears on the map at
the next reload, with no file to regenerate.

**2. Why does settings.py read the database password from an environment variable?**

settings.py is committed to GitHub, so anything written in it is visible
to anyone who can see the repository, and stays in the Git history even
if removed later. Reading it from `WEBGIS_DB_PASSWORD` keeps the secret on
this machine only, and lets each machine (or a later server) use its own
password without changing the code.

**3. What does the index created USING GIST do, and which query benefits from it?**

It is a spatial index (an R-tree built on each geometry's bounding box).
Instead of testing every polygon, PostGIS first uses the index to find the
few districts whose bounding box contains the search point, and runs the
exact, expensive geometry test only on those. The Part 8 query benefits:
`geom__contains=point` in `district_at`, which becomes `ST_Contains` in
SQL, both through `/api/where/` and when run by hand in pgAdmin.

**4. What would happen without wrapping some geometries in a MultiPolygon?**

The `geom` column is `geometry(MULTIPOLYGON,4326)`, so it accepts only
multipolygons. The file holds 152 Polygon features and 8 MultiPolygon
features. Without the wrap, the first Polygon insert would be rejected
because its geometry type does not match the column type, the script would
stop with an error, and the table would be left incomplete. Wrapping a
polygon as a one-part multipolygon changes nothing on the map but matches
the column type.

**5. Who should have an admin login for a district dataset like this, and who should not?**

Only the people responsible for maintaining the data: the GIS or data
staff who correct boundaries and enter census figures, each with the
smallest permissions their job needs (for example, change but not delete).
The public, map viewers, and anyone who only needs to read the data should
not have one; they use the map and the API. Admin access can change or
delete every row, so it should be limited, individual and accountable
(each edit is logged under the user's name in History).

**6. Leaflet takes [lat, lng] and Point takes (lng, lat). Where is each order used, and how does the extension's URL avoid confusing them?**

- **lat, lng (Leaflet):** `setView([30.3753, 69.3451], 5)`, the
  `maxBounds` corners, and `e.latlng` in the map click handler.
- **lng, lat (GEOS, GeoJSON, PostGIS):** `Point(lng, lat, srid=4326)` in
  `district_at`, the coordinates inside the GeoJSON from
  `/api/districts/`, and `ST_MakePoint(72.9906, 33.6423)` in the SQL.

The URL `/api/where/?lat=33.6423&lng=72.9906` passes the two values as
named parameters, and the view reads them by name
(`request.GET["lat"]`, `request.GET["lng"]`). Their order in the URL
therefore does not matter, and the view itself puts them into `Point` in
the order GEOS expects.

## 6. Notes

This project runs only on a local machine: GitHub Pages serves static files
and cannot run Python or a database, so there is no live URL for this lab.
To run it: create the venv, `pip install -r requirements.txt`, set
